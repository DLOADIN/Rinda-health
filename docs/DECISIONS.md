# Architecture decisions
Short records of decisions that are already made. Do not reopen one without the user's agreement; add a new record that supersedes it instead.

## ADR-001: Progressive web app, not native apps
**Context.** One student developer, a five-week build, participants on Android and iOS, a facilitated pilot. **Decision.** Build one installable PWA (C-01; user decision, 28 September 2026). **Consequences.** One codebase and instant updates. iOS limits (no Background Sync, storage eviction rules) are handled by syncing whenever the app is open and keeping local data short-lived.

## ADR-002: Node.js and TypeScript only, no Python
**Context.** The user decided the proposal and the system use no Python (28 September 2026). **Decision.** Every server component, script, hook and tool is TypeScript or JavaScript on Node.js (C-02). **Consequences.** Shared types and the shared rules package across client and server. A repository hook blocks creating `.py` files and running Python.

## ADR-003: Deterministic, versioned ruleset in one shared package
**Context.** Results must be reproducible, explainable and identical offline and online (FR-09, NFR-10). **Decision.** Pure TypeScript rules in `packages/rules`; thresholds in a versioned ruleset JSON that goes through content approval. No ML (C-03). **Consequences.** Golden fixtures run in Node and in the browser build; any change needs a new ruleset version.

## ADR-004: Monorepo with npm workspaces
**Decision.** `apps/web`, `apps/api`, `packages/rules`, `packages/schemas`, `packages/content` in one repository with npm workspaces (SRS Section 9). **Consequences.** One install, one CI pipeline, typed contracts shared through `@rinda/schemas`.

## ADR-005: shadcn/ui is the only component library
**Context.** The user asked for shadcn components only and the "Vibrant but Calm" palette (4 October 2026). **Decision.** Every interface element is composed from shadcn/ui components added with the shadcn CLI and themed by `docs/design/rinda-theme.css`. No other UI kit, icon set (lucide-react only) or CSS framework. Initialise with the **Radix** base (`npx shadcn@latest init -b radix`); since July 2026 the CLI defaults to Base UI, and the Radix primitives are the more mature choice for this build. **Consequences.** Consistent, accessible primitives; we own the component source and may adjust variants (for example 44 px button heights). A repository hook blocks installing other UI libraries.

## ADR-006: Offline-first with an encrypted outbox
**Decision.** Encrypted IndexedDB drafts and outbox, on-device scoring, idempotent submissions, sync on open, online and visibility events, Background Sync only as a bonus (FR-08, FR-28 to FR-31). **Consequences.** Works on Safari, which lacks Background Sync. Results shown offline are provisional until the server re-score confirms them.

## ADR-007: The AI guide is a bounded workflow
**Context.** The user asked for an AI agent; the ethics approval and C-03 rule out generative AI in the MVP; proposal Section 1.10.7 allows rewording only, after new approval. **Decision.** The guide's planner, coach and template composer are deterministic and ship in the pilot. An AI explainer rewrites template answers, receives no tools, never sets numbers, bands, safety or referral text, and stays behind `guideGenerative`, which cannot be enabled without `ETHICS_AMENDMENT_REF`. **Consequences.** The guide is useful from day one and the AI layer can be switched on later without redesign. See [AI_GUIDE.md](AI_GUIDE.md).

## ADR-008: One content table with two-person approval
**Decision.** All versioned content types share a `ContentVersion` table; publishing needs two approvals from two different people with the required reviewer types (FR-20, FR-46). **Consequences.** One approval workflow and one diff view for every content type.

## ADR-009: Staff console inside the web app, code-split
**Decision.** `/staff/*` routes live in `apps/web`, load on demand and are excluded from the service-worker precache. **Consequences.** One design system and one deployment; participants never download staff code.

## ADR-010: Redux Toolkit with RTK Query
**Decision.** Redux Toolkit for app state and RTK Query for API calls (SRS Section 9). Drafts and the outbox persist through the encrypted IndexedDB layer, never through `localStorage`. **Consequences.** Predictable state and caching; no plaintext persistence.

## ADR-011: Express 5, Zod and pino on the API
**Decision.** Express 5 with Zod `strictObject` validation from `@rinda/schemas`, Prisma for data access, pino with redaction for logs, Argon2id for secrets. **Consequences.** One validation language across the stack and logs that are safe by construction.

## ADR-012: No third-party analytics
**Decision.** No analytics, tracking pixels, crash reporters or CDNs that see participant traffic (NFR-02). Pilot evaluation data come from facilitator task records, feedback forms and aggregate first-party insights (FR-45, FR-47). **Consequences.** Network inspection shows only first-party requests.

## ADR-013: Pin Prisma ORM 7 for the pilot
**Context.** On 4 October 2026 `npm i prisma` installs the Prisma 8 release candidate, a rewrite with a new client and tooling. Prisma 7 is the stable line, needs a driver adapter and is ESM only. **Decision.** Pin `prisma`, `@prisma/client` and `@prisma/adapter-pg` to `^7` and follow the setup in [ARCHITECTURE.md](ARCHITECTURE.md). **Consequences.** No release-candidate surprises during the five-week build. Revisit after the pilot, once Prisma 8 is stable.

## ADR-014: PostgreSQL on Neon for every environment
**Context.** The user chose Neon-hosted PostgreSQL (4 October 2026). On 5 October 2026 the user reported that the supervisor confirmed the study may hold pilot data on this hosting, provided any personal identifiers that are collected are deleted within about 72 hours. **Decision.** Development, staging and the pilot use Neon PostgreSQL 16 or later through Prisma 7: the pooled connection (`DATABASE_URL`) for the running API and the direct connection (`DIRECT_URL`) for migrations. The earlier Rwanda-only or Article 50 requirement (C-07, NFR-14) is replaced by this approval. Data minimisation is unchanged: the app still collects no names, phone numbers, ID numbers or emails of participants (C-06), so there is no participant PII to delete; staff emails are the only direct identifiers and are not participant data. **Consequences.** Keep the supervisor's written confirmation with the ethics documents as the hosting record. Synthetic data only until ethics approval (C-08). If PII collection is ever added, it needs a deletion job that runs within 72 hours and a new ADR.

## ADR-015: Staff sign in with Google or an SMS code; participants keep study codes
**Context.** On 6 October 2026 the user asked for sign-in with Gmail or a phone number. They chose to apply it to staff only, with a "Sign in with Google" button and SMS one-time codes. **Decision.** Staff (researcher-admin, facilitator, reviewer) sign in with Google (OpenID Connect with PKCE, pre-registered emails only) or a 6-digit SMS code to a pre-registered phone. Researcher-admins keep an email and password break-glass sign-in for provider outages. Authorisation is role-based and deny-by-default (SRS Section 12, FR-51 to FR-55, NFR-19). Participants keep the study code and PIN (FR-03), so C-06 and the approved ethics protocol are unchanged for them. **Consequences.** Google and an SMS provider become third parties that see staff identifiers only. The SMS provider still needs to be chosen. New environment variables (Google client ID and secret, SMS provider key) go in the secret store. Staff identifiers are deleted when the project ends.

## ADR-016: `frontend/` and `backend/` folders, one backend file, plain SQL (no ORM)
**Context.** On 7 October 2026 the user asked for the code to be split into `frontend` and `backend` folders, for the whole API to live in one Node.js file, and for plain SQL instead of an ORM. **Decision.** `frontend/` holds the React PWA; `backend/server.ts` holds the entire API (configuration, logging, database access, sessions, Google sign-in, every route, and the `migrate`, `seed` and `db-check` commands); `backend/db/migrations/*.sql` holds the PostgreSQL schema as plain SQL; the shared `packages/` (rules, schemas, content) stay where they are so web and API still score with the same code (FR-09). The `pg` driver runs parameterised SQL; Prisma is removed. This supersedes ADR-013 and the Prisma parts of ADR-011 and SRS Sections 3.3 and 9. **Consequences.** No generated client or ORM migrations: a schema change is a new numbered `.sql` file that `npm run db:migrate` applies once. Every query uses `$1` parameters, never string building with values. The single file is long (about 2,200 lines) and is organised in numbered sections.

## ADR-017: Open sign-up for every role, with email or phone and a password
**Context.** On 7 October 2026 the user chose open sign-up for all roles (participant, facilitator, researcher-admin, reviewer), with participants signing up by email or phone number and a password, or with Google. This replaces study codes and PINs (FR-03, FR-26), invite-only staff accounts (FR-54) and the "no participant email or phone" part of C-06. **Decision.** `POST /api/v1/auth/signup` creates an active account with the chosen role; participants get an AB/BA order at random. Passwords use Argon2id; five wrong passwords lock the account for 15 minutes; sessions are an HttpOnly cookie whose SHA-256 hash is stored. Staff screens show participants by a masked identifier only. **Consequences and risks.** Anyone who signs up as researcher-admin can manage users, publish content and see study data, so open sign-up must be closed or moderated before real data are collected. Participant emails and phone numbers are personal data: the ethics committee should be told, and they are removed when a deletion request is completed. When the supervisor's 72-hour deletion rule (ADR-014) starts counting still needs confirming.

## ADR-018: Dashboard skeleton from Badget, colours from Rinda
**Context.** On 7 October 2026 the user supplied github.com/Codehagen/Badget as the layout to follow, keeping the Rinda palette. **Decision.** The signed-in screens use the same shadcn `dashboard-01` structure as Badget: an inset Sidebar with a primary quick action, the role's menu, Profile and the account card; a header with the sidebar toggle and page title; gradient section cards for metrics; and a centred sign-in card with a large heading. Colours, fonts and band styles still come only from `rinda-theme.css`; icons stay lucide-react (Badget's Tabler icons are not used). The local `Badget-main/` copy is a design reference only and is ignored by Git and the tooling.

## ADR-019: Google Gemini (free tier) for the Rinda Guide explainer
**Context.** On 9 October 2026 the user chose the Gemini free tier for the AI advice (AI_GUIDE.md). **Decision.** The explainer in `backend/server.ts` (section 5b) calls the Gemini `generateContent` API with structured JSON output, using `GEMINI_API_KEY` and `GEMINI_MODEL` (default `gemini-3.5-flash`), through plain `fetch` (no new package). Everything else in AI_GUIDE.md still applies: the rule-based template answer is composed first (offline, in `packages/rules/src/guide.ts`); only NCD band codes, band words, values and plan targets are sent, never identifiers, dates or mental-wellness data; the deterministic validator (numbers, sources, banned words, scope, length) must pass or the template is shown; Kinyarwanda, urgent results and safety events stay template-only; at most 20 generated answers per participant per day; `guide_request_log` keeps no participant ID, prompt or answer text. The API keeps the AI off unless `ETHICS_AMENDMENT_REF` is set, and refuses a `SYNTHETIC…` placeholder when `APP_ENV=pilot`. Each participant must also opt in separately (consent scope `ai_explanations`, a Profile switch that starts off, `PUT /api/v1/participant/ai-explanations`); without it the template is served. In the pilot the API also requires `GEMINI_PAID_TIER=true`, a confirmation that the key is on a paid tier whose terms exclude training on prompts. Each AI answer is generated once per check-up, question and language, saved in `guide_answers` (deleted with the check-up, and cleared when the opt-in is withdrawn) and reused after that. Every Gemini attempt counts towards the daily limit, and completing a deletion request also removes the person's `message_events`. Guide feedback updates a log row by its random ID without an ownership check; the row holds no participant ID, so this is accepted. On a shared phone the cached profile (`cache:me`) is replaced at the next sign-in and cleared at sign-out and Exit. **Consequences and risks.** Free-tier prompts may be used by Google to improve its products, which is a poor fit for health data: use synthetic data only, and move to a paid tier or another provider with a no-training commitment before any amendment covers real participants.

## ADR-020: Email reports through Brevo, with results, opt-in only
**Context.** On 10 October 2026 the user replaced the planned WhatsApp and SMS notices (withdrawn until a later decision) with email reports, chose to include results, and chose Brevo's free plan (300 emails a day). **Decision.** A participant who switches on "Email me my check-up summaries" in Profile (consent scope `email_reports`, off by default, only for accounts with an email address) gets each new check-up's summary by email, and can send one again with "Email me this summary" (at most 5 a day). The email is built only from approved content: each NCD area's result word, the first small step, the educational notice and a link to the result in Rinda. Mental-wellness results are never emailed. The backend calls Brevo's `POST /v3/smtp/email` with plain `fetch` (no new package), from a sender verified in Brevo (`BREVO_API_KEY`, `EMAIL_FROM`, `EMAIL_FROM_NAME`). `message_events` records channel `email`, status and error code, never the address or text, and is deleted with the account. The `messaging` flag is on in development and off in the pilot profile; the pilot refuses to switch it on until `MESSAGING_APPROVAL_REF` holds the ethics approval reference. **Consequences and risks.** Health results leave the system to Brevo (an EU processor) and sit in the participant's inbox, where anyone with access to that email can read them; the ethics committee must approve this and the consent text must say so. Without a verified own domain, some emails may land in spam.

## ADR-021: Mental-wellness module, consent gate, SUS and 72-hour deletion
**Context.** On 11 October 2026 the user asked for the mental-wellness module, consent and eligibility at the start, withdrawal and deletion, the SUS questionnaire and the "How results are calculated" page; facilitator tools and the skipped-item-9 decision were left out. **Decision.** The PHQ-9 and GAD-7 run inside the check-up after an introduction that needs an explicit choice (FR-22), only for participants who gave the mental-wellness consent. Item 9 above 0 is checked synchronously on the phone and shows the safety screen before anything is sent; one Tier 2 event per check-up is queued encrypted, per account, and sent once (FR-11, FR-13, FR-41). Tier 1 is recorded by the server from the score. Safety wording stays with the mental-health reviewer (placeholders until then). New participants see the purpose, an 18 to 35 age check and four separate un-ticked consents before any question, and the API refuses check-ups without core consent (FR-01, FR-02). Optional consents change from Profile; withdrawing core consent is a deletion request, completed within 72 hours. SUS answers are stored per item with the form version, and the admin dashboard shows the average score (FR-17). The rules page fills approved sentences with numbers read from the ruleset (FR-23). **Consequences.** The Kinyarwanda PHQ-9, GAD-7 and SUS texts are drafts to be replaced by validated versions; consent wording must match the ethics-approved form; airplane-mode browser tests for item 9 need a signed-in test account and are still to do.

## ADR-022: Landing page, split sign-in pages, Magic UI blocks and stock photos
**Context.** On 12 October 2026 the supervisor asked for a public landing page and better sign-in and sign-up pages (references: functionhealth.com and five Dribbble shots). The user allowed Magic UI / Aceternity blocks and free stock photos. **Decision.** The public pages use a full-width `PublicShell` (floating glass nav, language switch, Exit, floating Get help now) instead of the narrow `AppShell`. The landing page has hero (with a live phone mockup built from the app's own components), stats, an areas marquee, features, how it works, made for Rwanda, privacy, about us, FAQ, contact (m.david@alustudent.com, +250 791 291 003) and a closing call to action. Sign-in and sign-up use a split layout with a rotating photo panel. Magic UI blocks are copied in by hand as CSS-only components (`components/magicui`: marquee, border beam, dot pattern, shimmer button), so no animation package is added and the guard hook stays as it is; all motion stops under `prefers-reduced-motion`. Six free Unsplash photos (Unsplash License, checked through the free download link) are self-hosted as WebP in `public/images/landing`, loaded lazily and not precached. To stay inside the 250 KB first-load budget, the landing page and the sign-in panel text load with their pages (`locales/*/landing.json`), and the Kinyarwanda interface text loads the first time someone switches to it. **Consequences.** The shadcn-only rule now has a documented exception for these hand-copied blocks; the landing wording is interface text, not approved health content, and still needs the language reviewer.

## ADR-023: WhatsApp notices return, before SMS
**Context.** On 12 October 2026 the user asked for WhatsApp messages when results are ready, before any SMS work (SMS provider still being researched). **Decision.** WhatsApp "your summary is ready" notices come back next to email reports, through the Meta WhatsApp Cloud API with plain `fetch`. Each channel has its own opt-in: consent scope `whatsapp_notices`, a Profile switch that starts off and needs a phone number (`GET/PUT /api/v1/participant/whatsapp`). The message is an approved template with no parameters, so results can never be included. `message_events` records channel `whatsapp`, template name, status and error code only. Sending also needs the `messaging` flag (off in the pilot profile and refused there without `MESSAGING_APPROVAL_REF`). Migration `008_whatsapp_notices.sql` allows the channel and scope again. **Consequences.** Needs a Meta developer app, a WhatsApp phone number ID, a permanent token and an approved template named `rinda_summary_ready` (`WHATSAPP_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`). Phone numbers go to Meta only for people who opted in.

## ADR-024: Live session console and one-click research report
**Context.** On 12 October 2026 the user asked for features that would impress facilitators, and chose to start with a live session console and a research report (QR phone set-up waits for approval of a QR package). **Decision.** While a facilitated session is open, the participant's app reports the study step it is on (sign in, consent, questionnaire, measurements, results, get help) to `POST /participant/session-progress`, with a heartbeat every 20 seconds; only step names and times are stored (`session_progress`, migration 009). The session's facilitator sees `GET /facilitator/sessions/:id/live` every 3 seconds: current step and time in it, a timeline, whether the phone is connected, and a calm alert for any safety event since the session started; each task row can take the live time as its duration. Researcher-admins get `GET /admin/research-report` (aggregate counts only: consents, check-ups, task outcomes and median times, SUS mean, median, range and bands, latest NCD result per participant, safety tiers, languages), shown at `/app/research` with a CSV download and a print view that saves as PDF. Viewing the report is written to the audit log. **Consequences.** No answers, scores or identifiers reach the facilitator console or the report; with 15 participants some counts are small, so the report is for the research team only.

## ADR-025: QR set-up and wipe for study phones
**Context.** On 12 October 2026 the user approved the `qrcode` package for the third facilitator feature. **Decision.** On a session page the facilitator shows a one-time QR code (valid 15 minutes, only its SHA-256 hash stored in `session_devices`, migration 010). The study phone opens `/setup/:code`, claims it (`POST /api/v1/devices/claim`, rate-limited) and receives a device token (also stored only as a hash), switches to the participant's language and goes to sign-in. The token is kept in the encrypted vault; a small lazily loaded watcher, started on the sign-in page and the participant screens (never on the landing page), asks `GET /api/v1/devices/status` every 15 seconds. "End session and clear phone" (`POST /facilitator/sessions/:id/wipe`) ends the session and flags the phone; the phone sends anything still waiting, signs out, clears every vault entry, confirms with `POST /api/v1/devices/wiped`, and shows the neutral screen. An unknown token is also told to wipe. The facilitator's live console shows linked, clearing and cleared. Staff-only interface text now loads with the staff screens (`locales/*/staff.json`) to keep the first download under 250 KB. **Consequences.** A phone that stays offline after the session ends is cleared the next time it connects; facilitators should check for "Phone cleared" before handing the phone on.

## ADR-026: Reading the blood pressure monitor with the camera

**Context.** On 13 October 2026 the user asked for the blood pressure step to read a digital monitor's screen with the camera, on phones and in the desktop web app, to cut typing errors on the most important measurement. **Decision.** A small seven-segment reader written in TypeScript (`frontend/src/lib/bp-reader.ts`), with no OCR dependency. It smooths the picture, marks pixels darker and lighter than their surroundings, drops anything touching the edge or too large to be a segment, straightens slanted digits, and reads each row's segments. Both screen types (dark-on-light and backlit) are tried and a reading is offered only if they agree, only if the two top rows are the same size, and only if the values are plausible (systolic 60 to 260, diastolic 30 to 160, diastolic below systolic). With the live camera three frames must agree. The person always sees the numbers, checks them against the monitor and taps "Use these numbers"; the normal validation still applies. A photo can be used instead of the live camera, and the numbers can always be typed. The picture is read in memory, never stored or sent, and the camera is switched off as soon as a reading is found or the dialog closes. **Consequences.** It is tested on drawn screens (upright, slanted, backlit, grainy, with casing and frame lines; 60 poor pictures never give a wrong number) and in Chromium with a fake camera and WebKit with a photo. Accuracy on the pilot's real monitor model must be checked with real photos before the pilot.

## ADR-027: Offline hand-over by QR code

**Context.** On 13 October 2026 the user asked for a way to move results when the venue has no internet; on 14 October they approved `jsqr` for reading QR codes in every browser. **Decision.** A phone with check-ups or item 9 events waiting can show "Hand over to the facilitator". It seals them on the phone to the server's hand-over public key (a fresh ECDH P-256 key, HKDF-SHA-256, AES-256-GCM, gzip inside when available) together with an expiring per-person proof (HMAC of the user id and issue time, valid 30 days), and shows the package as a loop of QR codes. The facilitator's Collect page reads them with the laptop camera (the browser's reader when it supports QR codes, otherwise `jsqr`), puts the parts back together and keeps the sealed package in the laptop's encrypted vault, tagged with that facilitator, until it can be uploaded to `POST /api/v1/facilitator/handover`. The server picks the key by its id, opens the package, checks the proof and that this facilitator had a session with the participant in the last 14 days, stores safety events first, then the check-ups through the same code as a direct submission, with the same idempotency keys, and audits counts only. A package the server refuses stays on the laptop as "could not be delivered" until the facilitator discards it. In the pilot the key comes from its own `HANDOVER_SECRET` (required when `APP_ENV=pilot`), and `HANDOVER_SECRET_PREVIOUS` keeps older packages working during a rotation; elsewhere it falls back to the session secret. **Consequences.** The laptop can carry but never read a package. The phone keeps its own copies and still sends them itself when it is online; duplicates are impossible. Data passing through a facilitator device must be covered by the approved protocol before pilot data use it; this needs the supervisor's confirmation.

## ADR-028: Offline answer set for the guide

**Context.** On 13 October 2026 the user asked for the guide to give answers based on each person's own results when Gemini fails or the phone is offline. **Decision.** A separate approved-content file, `guide-answers.json` (English and Kinyarwanda, status in review, reviewers clinical and language), holds for every NCD area and result a short "why it matters" and "what helps" written for young adults in Rwanda. It is loaded only by the guide panel and the server (`@rinda/content/guide-answers`), so the first download does not grow. The deterministic composer in `@rinda/rules` adds these to "Explain my result" and to a new "What can I do about my results?" option, which covers the person's own focus areas, or what helps keep things as they are when nothing needs focus. Nothing is added where approved safety text already speaks ("Seek care today"), mood and stress are never mentioned, and a missing entry is left out rather than shown as an ID. The same entries join the library Gemini may draw from, so generated answers stay grounded in them. Content validation requires both entries for every area and result in every language. **Consequences.** The guide is useful with no internet and no AI. The wording must be approved by the clinical reviewer and the bilingual key informant before the pilot.
