1. Product overview and architecture

Rinda Health is a bilingual (English and Kinyarwanda), offline-first progressive web app (PWA). It helps Rwandan adults aged 18–35 screen six non-communicable disease (NCD) risk factors: tobacco, alcohol, physical activity, fruit and vegetables, body size and blood pressure. People can also take an optional mental-wellness check (PHQ-9, GAD-7). Each area gets its own explained, educational result, with a short weekly plan and links to real services. The product is educational, not diagnostic, and it is not an emergency service. Four roles share one app: participant, facilitator, researcher-admin and reviewer.

3. Technical functionality

FeatureHow it works (technical logic)
Accounts and rolesRoutes in the auth router. Passwords are hashed with Argon2id; Google sign-in uses OpenID Connect with PKCE. Session cookies are HttpOnly and SameSite, with 8 h idle and 12 h absolute limits. requireRole() guards every staff route, and each staff action is written to the audit log.
Check-up and scoringReact Hook Form validates with Zod schemas from packages/schemas. A skipped answer is stored as a missingness code, never as 0. scoreAssessment() is a pure function: it runs on the phone for instant and offline results, and again on the server, which stores the authoritative copy with its ruleset version.
SafetycheckItem9() runs on the phone before any network call and opens the safety screen. checkChatQuestion() blocks crisis phrases and personal data before any AI call. In the voice check-up, item 9 can only be answered by tapping, to avoid mis-hearing.
Offline and syncThe service worker precaches the app shell. Offline check-ups are encrypted with AES-GCM 256 (Web Crypto, a non-exportable device key, lib/storage/vault.ts) in IndexedDB, then sent in order when online with an Idempotency-Key. The server stores a SHA-256 hash of the canonical body, so a resend returns the first result.
AI guide and chatA provider chain (Gemini → Groq → OpenRouter) is tried in order. Every answer passes validateGuideAnswer, which accepts only approved source IDs and numbers taken from the person's own results; otherwise the approved template is shown. Each person can ask 15 questions a day.
Voice check-upEach question is spoken by a text-to-speech chain (Groq → ElevenLabs → Gemini → browser voice). Clips are cached in voice_clips under a SHA-256 key, and only approved content IDs can be spoken. Answers are heard with the browser's speech recognition and parsed by a deterministic parser (voice-parse.ts) into the same form.
Email and SMSAfter a check-up is saved, sendReportEmail (Brevo) and sendSmsReport (Pindo) run after the response through Vercel waitUntil. Each respects the person's on/off switch. Outcomes are logged to message_events as status only, with no content.

Frontend–backend–data flow. RTK Query (lib/api.ts) calls /api/v1/…. Express parses each body with a strict Zod schema (unknown fields → 400 with a stable error code). Plain parameterised SQL ($1) writes to Neon, and schema changes are numbered SQL migrations. RTK Query cache tags refresh the affected screens. Logs (pino) never contain answers, results, passwords or tokens, and a sentinel test enforces this.

4.3 Performance and compatibility

The live site was measured with a Playwright script: cold load, median of 3 runs, on 1 November 2026. The low-end profile emulates a mid-range Android on Slow 4G (1.6 Mbps, 150 ms latency) with a 4× CPU slowdown.

Analysis. Even on the low-end profile the first content shows in about 3 s, under the 4 s "poor" Largest Contentful Paint line; on fast networks it is 1.8–2.2 s on Chromium, close to the 2.5 s "good" target. The page stays light (about 365 KB transferred, 9.5 MB JavaScript heap) because heavy features load only when opened. On a repeat visit the service worker serves the app from its cache: it loaded in 0.13 s on the fast phone profile and 0.32 s on the low-end one (median of 3), well inside the proposal’s 1 s target, and it reloaded fully with the network switched off. Compatibility is covered by running the same end-to-end suite on Chromium (Chrome, Edge and Samsung Internet on Android and Windows) and WebKit (iPhone and iPad Safari) at 360 px phone width and on laptop screens. Remaining limits: speech recognition is not available in every browser (the voice check-up hides itself and the form stays usable), and Kinyarwanda voice is not available yet.

5. Code quality and technical implementation

5.1 Structure and separation of concerns

The code is an npm-workspaces monorepo. frontend/src/features/* holds one folder per area (auth, consent, participant, results, guide, profile, dashboard, staff, sync). components/ holds reusable compositions (AppShell, GetHelp, BandBadge, ConfirmAction), and lib/ holds infrastructure (API client, offline outbox, encrypted storage, i18n, BP reader, voice). The most important logic, scoring, safety and planning, is not in the UI or the API. It lives in packages/rules as pure, framework-free functions, so it has one source of truth, works offline and is easy to test. packages/schemas owns every data contract, and packages/content owns every participant-facing word. The API is a single deployable file for simple serverless hosting. Inside it, each area is its own Express Router (15 routers: auth, account, participant, facilitator, admin, content, dashboard, guide, chat, voice, messaging and others), built by createApp() from injected dependencies.

5.2 Object-oriented principles applied

PrincipleWhere and how
AbstractionRuleset, DomainResult, AssessmentResult, Plan types (packages/rules/src/types.ts). Callers use scoreAssessment() without knowing any per-area rule.
Encapsulationlib/offline.ts keeps the outbox queue private and exposes only addToOutbox, flushOutbox and useOutbox; lib/storage/vault.ts hides the non-exportable AES key behind encrypt/decrypt calls.
InheritanceAppError extends Error carries an HTTP status and a stable code, so one error handler serves every route. GuideBoundary extends React.Component isolates guide failures.
PolymorphismAI and voice providers share one interface: the chain calls askGemini, askOpenAiStyle (Groq, OpenRouter, Cerebras, Mistral) or speakGroq/speakElevenLabs/speakGemini the same way and falls back on failure. The seven per-area scorers share one signature in a SCORERS strategy map, so scoreDomain() treats them alike.
Dependency injectioncreateApp({ config, logger, db, fetchFn }), so tests inject a fake fetch and a throwaway database schema with no code changes.
Reuse and single responsibilityShared packages are imported by both web and API. Schemas only validate, rules only compute, content only holds text. shadcn/ui components are themed once in rinda-theme.css.

5.3 Algorithms and problem solving

ProblemSolution
Identical results on every devicePure, versioned rules with integer arithmetic (BMI × 10, ages and minutes as integers). 79 golden cases run in Node, Chromium and WebKit to prove client–server parity.
Reading a BP monitor from a photoA pipeline that runs in the browser: grayscale, Otsu thresholding, morphological filtering with the van Herk/Gil-Werman sliding min/max (O(n) per row, whatever the window size), line and speckle removal, projection profiles to find digit rows, shear estimation for slanted digits, rotation for tilted photos, then seven-segment decoding. Several frames must agree before a value is accepted.
Choosing next stepsA priority planner: urgent areas first, then a fixed order, at most 3 focus areas. Targets are rounded to practical steps, e.g. "+20 minutes on 3 days".
Moving data with no internet (QR)The phone seals the check-up for the server only: ECDH P-256 key agreement, then HKDF, then AES-GCM 256, compressed to fit in a QR code. The facilitator relays it without being able to read it.
No duplicates on bad networksIdempotency key plus a SHA-256 hash of the canonical, key-sorted JSON body. Same key with the same body → replay; with a different body → 409.
Safe AI outputA validator whitelists source IDs and checks every number against the person's own results. The provider chain falls back on errors and time-outs, and a crisis and personal-data guard runs first.
Understanding spoken answersA deterministic parser normalises text, maps number words to digits, matches yes/no and choice synonyms, detects commands (skip, repeat, stop) and flags off-topic speech. A crisis check runs on every utterance.
Cheap, reliable SMSTypographic characters (curly quotes, dashes, ellipses) are replaced so the text stays in the GSM-7 alphabet and each part is billed at the lowest rate. An optional allow-list (SMS_ONLY_TO) limits sends during testing.

5.4 Quality practices, limitations and future work

  • TypeScript strict mode with no any; ESLint and Prettier enforced; kebab-case files and named exports; Zod at every boundary with stable error codes; no hard-coded participant text (all via i18n, both languages).
  • Privacy by design: data minimisation, encrypted local storage, masked identifiers for staff, audit log, consent switches, and no third-party analytics.
  • Over 200 commits with short conventional messages, plus CI on every push.
  • Limitations and next steps: split the API file's routers into separate modules after the pilot; build the What-if screen and clinic card; record and review Kinyarwanda audio; complete native-speaker and clinician content review; run the November pilot (15 participants, 5 key informants) with SUS usability scoring.
